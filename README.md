# مطعم الدولمة السحابي — Dolma Cloud Kitchen

نظام حجوزات وإدارة كامل لمطعم سحابي منزلي متخصص بالدولمة العراقية الفريش.
Frontend ثابت بالكامل (HTML/CSS/Vanilla JS) بدون أي Framework أو Build Step،
يعمل مباشرة على GitHub Pages ويتصل بـ Supabase (قاعدة بيانات + مصادقة).

## البنية

```
index.html          واجهة الزبون (اختيار النوع → الحجم → التخصيص → الحجز)
admin/index.html     لوحة إدارة المطعم (محمية بتسجيل دخول + RLS)
css/                 التصميم
js/customer/         منطق واجهة الزبون
js/admin/            منطق لوحة الإدارة
js/supabase-config.js  مفاتيح Supabase العامة (تعبئيها بنفسك، لا Secret Keys)
supabase/            ملفات SQL لإنشاء قاعدة البيانات
```

## خطوة 1: إنشاء مشروع Supabase

1. افتحي [supabase.com](https://supabase.com) وأنشئي حساباً/مشروعاً جديداً (اختاري منطقة قريبة من العراق إن توفرت).
2. من القائمة الجانبية: **SQL Editor → New query**.
3. نفّذي الملفات التالية **بالترتيب** (كل ملف في استعلام منفصل، انتظري نجاح كل واحد قبل التالي):
   1. `supabase/schema.sql`
   2. `supabase/rls_policies.sql`
   3. `supabase/functions.sql`
   4. `supabase/seed.sql` (اختياري — بيانات تجريبية فقط لتجربة النظام، عدّليها لاحقاً من لوحة الإدارة لتطابق أسعارك الحقيقية)

## خطوة 2: إنشاء حساب صاحبة المطعم (Admin)

الزبون لا يسجّل دخول إطلاقاً — فقط صاحبة المطعم تحتاج حساباً لدخول لوحة الإدارة:

1. من Supabase: **Authentication → Users → Add user** (أدخلي بريدك الإلكتروني وكلمة مرور).
2. بعد إنشاء الحساب، سيُنشأ تلقائياً صف مطابق في جدول `profiles` بدور `customer` (افتراضي آمن).
3. رقّي الحساب إلى `owner` من **SQL Editor**:
   ```sql
   update profiles set role = 'owner'
   where id = (select id from auth.users where email = 'بريدك@example.com');
   ```
4. الآن يمكنك تسجيل الدخول من `admin/index.html` بهذا البريد وكلمة المرور.

## خطوة 3: ربط الواجهة بمشروعك

1. من Supabase: **Project Settings → API**.
2. انسخي **Project URL** و **anon public key** (وليس `service_role` — هذا المفتاح سري ولا يوضع في الواجهة أبداً).
3. افتحي `js/supabase-config.js` وضعي القيمتين:
   ```js
   export const SUPABASE_URL = 'https://xxxxxxxx.supabase.co';
   export const SUPABASE_ANON_KEY = 'ey...';
   ```

## خطوة 4: التشغيل محلياً للتجربة

المشروع ثابت بالكامل (بدون Node.js)، لكن المتصفح يمنع `type="module"` من العمل عبر `file://` مباشرة،
لذا شغّلي أي خادم ثابت بسيط من داخل مجلد `dolma-restaurant`:

```bash
python -m http.server 8080
```

أو أي أداة مشابهة (Live Server في VS Code، إلخ). ثم افتحي:
- `http://localhost:8080/` لواجهة الزبون
- `http://localhost:8080/admin/` للوحة الإدارة

## خطوة 5: النشر على GitHub Pages

1. أنشئي repository جديد على GitHub وارفعي محتوى مجلد `dolma-restaurant` (بما فيه `js/supabase-config.js` بعد تعبئته).
2. من إعدادات الـ repository: **Settings → Pages → Deploy from a branch** → اختاري `main` والمجلد `/ (root)`.
3. بعد دقائق سيصبح الموقع متاحاً على رابط مثل: `https://username.github.io/dolma-restaurant/`
   ولوحة الإدارة على: `https://username.github.io/dolma-restaurant/admin/`

> **ملاحظة أمان**: `admin/index.html` سيكون قابلاً للوصول كصفحة عامة (أي رابط على GitHub Pages عام)،
> لكن هذا غير خطير لأن الحماية الفعلية مطبّقة داخل قاعدة البيانات نفسها عبر Row Level Security —
> بدون تسجيل دخول بحساب `owner`/`admin` حقيقي، لا يمكن قراءة أو تعديل أي بيانات إدارية مهما كان الوصول للصفحة.

## كيف يعمل الأمان (RLS)

- الزبون (`anon`) يرى فقط أنواع الدولمة والأحجام النشطة مباشرة، ولا يصل إطلاقاً لجداول المكونات
  أو الوصفات أو الطلبات أو العملاء أو التكاليف.
- كل تفاعل الزبون مع تفاصيل الوصفة وإرسال الحجز يمر عبر دالتين آمنتين فقط:
  - `get_recipe_customer_view(...)` — تُرجع فقط أسماء المكونات وتأثيرها على السعر، بدون أي بيانات تكلفة داخلية.
  - `create_order(...)` — تُعيد حساب السعر والتكلفة من جديد على السيرفر بناءً على اختيارات الزبون
    الفعلية (المكونات الموجودة في الوصفة)، ولا تثق بأي سعر قد يُرسَل من المتصفح.
- صاحبة المطعم فقط (دور `owner`/`admin` في جدول `profiles`) تملك صلاحية القراءة والتعديل الكاملة
  على المكونات، الوصفات، الأسعار، الطلبات، العملاء — مطبّقة كسياسات RLS حقيقية في Postgres،
  وليس مجرد إخفاء الصفحة بجافاسكربت.

## تعديل البيانات لاحقاً

كل ما تم زرعه في `seed.sql` (الأسعار، الكميات، المكونات) هو **بيانات تجريبية فقط** لتجربة تدفق النظام.
عدّلي الأسعار الحقيقية وكميات الوصفات وتكاليف المكونات من تبويبي **المكونات** و**الوصفات** و**الأسعار**
في لوحة الإدارة قبل الاستخدام التجاري الفعلي.

## هيكل قاعدة البيانات (ملخص)

| الجدول | الوصف |
|---|---|
| `dolma_types` | أنواع الدولمة الثلاثة |
| `pot_sizes` | أحجام الجدر (بما فيها "حسب الطلب") |
| `ingredients` | كل المكونات وطريقة حساب تكلفتها |
| `recipes` | وصفة لكل (نوع × حجم) — 9 وصفات، تفصل التكلفة عن سعر البيع |
| `recipe_ingredients` | مكونات كل وصفة + قواعد تأثيرها على السعر عند تخصيص الزبون |
| `customers` | سجل العملاء (يُطابق تلقائياً حسب رقم الهاتف) |
| `orders` / `order_selected_ingredients` | الطلبات وتفاصيلها الكاملة (Snapshot ثابت وقت الطلب) |
| `profiles` | حسابات الإدارة وأدوارها |
| `settings` | إعدادات عامة مرنة |

للتوسع لاحقاً (نظام مخزون/مشتريات): دالة `calc_ingredient_needs(from, to)` جاهزة بالفعل لتجميع
احتياج المكونات لأي مدى تاريخ استلام، وهي الأساس المطلوب لبناء نظام المشتريات لاحقاً.
